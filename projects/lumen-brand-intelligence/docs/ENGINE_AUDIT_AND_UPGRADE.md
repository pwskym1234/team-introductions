## 1. 결론부터

이 엔진은 사용자의 건강 질문을 받아 곧바로 상품을 추천하는 단순 추천기가 아니다. 현재 구현은 다음 순서로 작동한다.

1. 서비스 이용 동의가 있는지 확인한다.
2. 위험 증상과 보호 대상 여부가 확인됐는지 검사한다.
3. 정보가 빠졌다면 가장 중요한 질문 하나를 먼저 되묻는다.
4. 웨어러블 자료에서 변화 크기와 통계적 불확실성을 계산한다.
5. 변화·원인·위험·비교·정체·효과의 여섯 판정을 서로 구분해 만든다.
6. 사용자의 질문 의도와 관련 있는 상품만 검색한다.
7. 알레르기·금기·상호작용·라벨 누락 같은 문제를 점수 계산 전에 제거한다.
8. 안전 조건을 통과한 상품만 근거·개인 적합성·데이터 품질·실행 가능성으로 정렬한다.
9. 별도 브랜드 집계 동의가 있을 때만 개인정보가 제거된 이벤트를 만든다.

초기 코드의 엔지니어링 준비도는 **56/100**으로 평가했다. 안전 장치와 통계 계산의 기본 골격은 있었지만, 몇몇 경계 조건에서는 위험한 오판이나 잘못된 브랜드 지표가 만들어질 수 있었다. 이번 업그레이드 뒤 동일한 기준으로 다시 평가한 점수는 **82/100**이다.

이 점수는 의료적 안전성이나 임상적 유효성 인증 점수가 아니다. 소스 코드, 자동 테스트, 데이터 계약, 실패 시 동작을 평가한 **해커톤 데모 단계의 엔지니어링 준비도**다. 실제 사용자에게 제공하려면 임상 검토, 개인정보보호 체계, 실데이터 검증이 추가로 필요하다.

### 3.1 가장 위험했던 네 가지 문제

첫째, 사용자가 “심하게 토하고 배가 아픈데 약 용량을 줄여야 하나요?”라고 물으면 기존 순서에서는 `medication_boundary`가 `safety_stop`보다 먼저 나올 수 있었다. 처방 변경을 하지 않는다는 경계도 필요하지만, 응급 가능성이 있는 증상 안내가 더 먼저여야 한다.

둘째, `symptoms: []`는 두 가지 뜻일 수 있다. 실제로 증상이 없다고 확인했을 수도 있고, 아직 질문하지 않았을 수도 있다. 기존 엔진은 이를 구분하지 않고 위험 신호가 없다고 표현했다.

셋째, 단백질 보완 질문에도 종합비타민처럼 무관한 상품이 후보 평가에 들어갔다. 이 상품의 라벨이 빠져 있으면 실제 사용자 의도와 관계없는 결측이 브랜드 대시보드에 잡힐 수 있었다.

넷째, 브랜드 분석 이벤트가 서비스 처리 과정에서 자동 생성됐다. 서비스 제공 동의와 브랜드 집계 동의는 목적이 다르므로 별도로 통제해야 한다.

| P1 | 통계 빈 값 | 빈 구간을 `NaN`으로 내보냄 | 값이 없으면 명시적으로 `null` | API와 화면에서 “계산 불가”를 정확히 구분 가능 |
| P1 | 매우 작은 p값 | 반올림 결과가 `0`이 될 수 있음 | 안정적인 꼬리 계산과 유효 숫자 보존 | “확률이 정확히 0”이라는 잘못된 표현을 피함 |
| P1 | 이벤트 순서 | 모든 이벤트가 같은 시각 | `eventSequence`와 순차 시각 부여 | 질문→안전 확인→후보→노출 순서를 재구성 가능 |

## 6. 현재 엔진이 실제로 결정하는 방식

### 6.1 예시: “증량 뒤 잘 못 먹어요. 단백질 제품을 골라 주세요”

엔진은 먼저 상품을 찾지 않는다.

1. 위험 신호 질문이 완료됐는지 본다.
2. 성인 여부, 임신·수유, 섭식장애 우려, 알레르기를 확인한다.
3. 하나라도 `unknown`이면 가장 안전 영향이 큰 질문 하나를 반환한다.
4. 모두 확인됐으면 투약 사건 전후의 웨어러블 변화를 계산한다.
5. 질문의 `PROTEIN_SUPPORT` 같은 의도 코드와 맞는 상품만 가져온다.
6. 알레르기, 진단 금기, 의료진 식이 제한, 성분 중복, 미검증 상호작용, 라벨·근거·가격·재고 문제를 검사한다.
7. 통과한 상품만 점수로 정렬한다.

즉, 점수가 높아도 안전 필터에 걸린 상품은 절대 다시 살아나지 않는다.

### 6.2 여섯 판정은 서로 다른 질문에 답한다

| 판정 | 답하려는 질문 | 현재 한계 |
|---|---|---|
| 변화 | 개인 기준선에 비해 실제로 달라졌는가 | 임상적 위험을 뜻하지 않음 |
| 원인 | 변화 시점과 투약 사건이 겹치는가 | 인과관계를 확정하지 않음 |
| 위험 | 지금 상품보다 의료 확인이 먼저인가 | 진단을 하지 않음 |
| 비교 | 비슷한 사용자와 비교하면 어디인가 | 승인된 코호트가 없어 닫혀 있음 |
| 정체 | 장기간 변화가 멈췄는가 | 검증된 장기 규칙이 없어 닫혀 있음 |
| 효과 | 특정 상품이나 개입이 이 사용자에게 효과가 있었는가 | 승인된 n-of-1 프로토콜이 없어 닫혀 있음 |

비교·정체·효과를 억지로 숫자로 채우지 않는 것은 미완성이면서 동시에 안전 장치다. 데이터가 없을 때 그럴듯한 결론을 만들지 않는다.

### 6.3 브랜드 이벤트가 생기는 조건

다음 세 조건을 모두 만족해야 한다.

1. 서비스 제공 동의가 있다.
2. 별도의 `brand_aggregate` 동의가 있다.
3. 사용자가 동의한 정책 버전이 현재 엔진 설정과 일치한다.

조건이 맞지 않으면 결정 자체는 서비스 목적 범위에서 만들어질 수 있지만 브랜드 이벤트 배열은 비어 있다. 브랜드 도구에는 질문 원문, 증상 문장, 약명, 용량, 실제 사용자 ID가 들어가지 않는다.

| 임상 안전 규칙 검증 | 개발 규칙과 합성 사례만 있음 | 독립 임상의 검토, red flag 목록·문구·전환 경로 승인, 변경 이력과 승인자 기록 |
| 응급 상황 안내 | 일반 의료기관/응급 도움 안내 | 국가·지역별 긴급 연락, 지연 없는 안전 화면, 접근성·다국어 검증 |
| 동의 철회·삭제 | 요청 시점 정책 버전만 검사 | 동의 원장, 철회 이후 이벤트 차단, 과거 데이터 삭제·집계 재처리, 감사 로그 |
| 가명화 키 관리 | 고정 namespace SHA-256 데모 | tenant별 HMAC 비밀키, 회전·폐기 절차, 재식별 위험 검토 |
| tenant 격리 | 단일 데모 범위 | 저장소·쿼리·캐시·내보내기 전 구간 tenant 격리 테스트 |
| 상품 라벨 출처 | 합성 URL과 수동 상태 | 원본 라벨 provenance, 수집 시점, 검수자, 변경 감지, 서명 또는 무결성 검증 |
| 알레르기·성분 ontology | 단순 정규화 문자열 비교 | 검수된 원료 코드, 동의어·복합원료·교차오염 문구 처리, 고위험 회귀 세트 |
| GEO 파서 품질 | intentCodes가 정확하다고 가정 | 안전 증상·의도·제약 추출 precision/recall, 부정문·오타·다국어·적대 입력 평가 |
| 데이터 전송 신뢰성 | 메모리 이벤트 생성·집계 | transactional outbox, idempotency key, 재시도, 순서 뒤바뀜·유실·중복 복구 |

### 9.2 P1 — 제한적 파일럿 전에 해결

| 남은 위험 | 필요한 작업 |
|---|---|
| 통계적 오경보율 | null 시뮬레이션과 합성 시계열로 “아무 일도 없는데 경보” 비율 측정, 지표 묶음·윈도우 사전 정의 |
| 요일·장기 추세·결측 | 요일 보정, robust scale, 계절성, 비무작위 결측을 비교 실험하고 한 분석 프로토콜로 고정 |
| 임상적 중요도 | 통계적으로 분명한 변화와 실제로 중요한 변화를 구분할 지표별 최소 중요 변화 기준 검토 |
| 검색 재현율 | intent–상품 지원표의 정답 세트를 만들고 누락률·무관 후보율을 측정 |
| 상호작용 지식 | 약물·건기식 상호작용 데이터 출처, 갱신 주기, 전문가 검토 SLA 구축 |
| 질문 우선순위 | 실제 답변률·안전 영향·후보 변화량으로 `priorityScore`를 검증하되 안전 순서는 고정 |
| 관측성 | 규칙 버전별 안전 중단률, 미확인률, 데이터 결측률, 이벤트 유실률 모니터링과 경보 |
| 데이터 보존 | 목적별 보존 기간, 집계 최소 인원, 작은 셀 억제, 내보내기 권한 정책 |

### 9.3 P2 — 제품 고도화 단계

- 승인된 코호트 비교 모듈과 편향·표본 크기 기준
- 장기 정체 판정의 사전등록 규칙과 임상 검토
- 승인된 n-of-1 프로토콜, 순응도와 사전 정의 결과변수
- 사용자 설명 문구 이해도·불안 유발·과신 여부 테스트
- 인구집단별 누락과 과도한 안전 중단 차이 분석
- 브랜드가 수정할 수 있는 문제의 담당자·SLA·완료 상태 메타데이터
- safety KPI와 마케팅 KPI를 조직·권한 수준에서 분리하는 거버넌스

## 10. 현재 완료로 볼 수 있는 범위

다음은 코드와 테스트로 완료됐다고 볼 수 있다.

- 합성 데이터 기반 엔진 데모
- 안전 양성·안전 미확인의 상품 차단
- 처방 경계보다 안전 우선
- 여섯 판정의 독립 출력
- 의도 기반 상품 검색
- 하드 필터 뒤 점수 계산
- 알레르기 표시 누락 구분
- 동의 범위·정책 버전 기반 브랜드 이벤트 차단
- 개인정보 허용 목록 sanitizer
- 순서가 보존된 요청 단위 퍼널
- 가명 사용자 재방문 집계
- 33개 자동 테스트와 strict 타입 검사

다음은 완료됐다고 주장하면 안 된다.

- 의료기기 또는 임상 의사결정지원 시스템 검증
- 실제 상품 추천의 유효성과 안전성
- 약물 원인 판정
- 유사 환자 비교, 정체 판정, 개인 효과 입증
- 개인정보보호 법률 준수의 최종 승인
- 실제 브랜드 성과나 전환율 측정

## 12. 한 문장 평가

업그레이드 전 엔진은 “좋은 부품이 있지만 경계 조건에서 잘못된 결론과 잘못된 지표가 나올 수 있는 56점짜리 데모”였다. 현재 엔진은 “안전·미확인·동의·검색·이벤트 순서를 코드와 33개 테스트로 통제한 82점짜리 내부 검증용 데모”이며, 남은 18점은 주로 임상 검증, 개인정보 운영 체계, 실데이터 통계 검증에서 채워야 한다.
